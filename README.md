# TrustRail — Mobile Money Fraud Detection

A synthetic-data fraud detection pipeline for mobile money transactions: feature engineering, a gradient-boosted risk model, and a live Claude-powered explainability layer — packaged as an interactive monitoring console.

## What this demonstrates

This is a portfolio project, not a production system — real mobile money transaction data isn't available outside a licensed platform. What it's meant to show instead:

- **End-to-end pipeline thinking**, not just a model in a notebook — synthetic data generation, causally-correct feature engineering, model evaluation, and an explainability layer that a real analyst could use
- **Evaluation discipline** — precision-recall and precision@K instead of accuracy, a time-based train/test split, and a deliberate fix when an earlier version of the model scored a suspicious 100% (see [Known Limitations](#known-limitations))
- **A live AI integration**, not a mockup — the case-review console makes a real call to the Claude API to generate analyst-facing explanations

## Architecture

Four independent, testable stages:

**1. Synthetic Ledger** — 20,000 transactions across 2,000 users, with four injected fraud patterns (SIM-swap takeover, account takeover, smurfing, mule-velocity funneling). 30% of fraud cases are deliberately "stealthy," blending amount, timing, or device signals into the normal range so the dataset isn't trivially separable.

**2. Feature Engineering** — rolling per-user and per-recipient windows (1h/24h/7d velocity, 30-day amount z-score, device/SIM change flags, recipient account age) computed with strict time-causality using `bisect`-based binary search on sorted timestamps — every feature is derived only from what happened before that transaction.

**3. Risk Model** — a gradient-boosted tree classifier trained on a time-based 80/20 split (train on earlier transactions, test on later ones), which mirrors how it would actually be deployed and avoids leakage that a random split would introduce.

**4. Explainability** — the model's top contributing features are surfaced instantly as computed "signals." Selecting a flagged case then fires a real call to the Claude API, which writes a natural-language analyst note from those signals in real time.

### What actually drives the risk score

Permutation importance (drop in average precision when a feature is shuffled):

| Feature | Importance | What it captures |
|---|---|---|
| `recipient_account_age_days` | 0.588 | How new the money's destination account is |
| `amount_vs_user_avg_ratio` | 0.356 | How far the amount is from the sender's own norm |
| `time_since_last_txn_min` | 0.173 | Speed of repeat activity on the account |
| `is_new_device` | 0.036 | Whether the sending device is recognized |
| `txn_count_last_24h` | 0.023 | Transaction velocity in the past day |

Where the money is going, and how it compares to the sender's own history, matters far more than raw amount or device signals alone.

## Explainability, live

![Case review with live Claude explanation](https://github.com/Tundemachine/Trust-rail/blob/main/docs_images/case-review.png?raw=true)

Every flagged transaction shows two layers of reasoning: instant, deterministic "Signals" computed from the model's own top features, and an "Analyst Note" generated by a live call to the Claude API — not a template. This mirrors how a real fraud system would separate the automated risk score (which has to be fast) from the natural-language explanation (which doesn't need to block the transaction).

## Tech stack

- **Data generation & feature engineering:** Python, pandas, numpy
- **Model:** gradient-boosted trees (XGBoost-class), scikit-learn for evaluation
- **Explainability:** Claude API (live)
- **Console:** single-file HTML/CSS/JS — no build step, no server dependency

## Running it locally

```bash
# 1. Generate the synthetic transaction dataset
python generate_fraud_data.py

# 2. Build the model-ready feature table (rolling windows, z-scores, etc.)
python feature_engineering.py

# 3. Train and evaluate the model
python train_model.py

# 4. Open the dashboard
open fraud_detection_dashboard.html   # or just double-click it
```

Requires `pandas`, `numpy`, `scikit-learn`, and optionally `xgboost` (falls back to scikit-learn's `HistGradientBoostingClassifier` automatically if XGBoost isn't installed).

> **Note on the live Claude explanation:** the dashboard's "Analyst Note" calls the Anthropic API directly from the browser. This works out of the box inside Claude's artifact/preview environment, which proxies the request. If you host this file elsewhere (Netlify, Vercel, GitHub Pages), that call will fail without a backend — you'd need a small proxy server holding your own Anthropic API key.

## Known limitations

- All data is synthetic — no real mobile money platform data was used or is represented here
- The mule-detection network feature (unique senders to a recipient) shows limited signal in the current dataset and needs a longer-horizon graph feature to properly capture collusion patterns
- An earlier version of the synthetic data produced a suspicious 100% precision/recall score — treated as a red flag rather than a result, and fixed by adding realistic overlap between legitimate and fraudulent behavior before moving forward
- The live Claude explanation requires the artifact/preview environment's API proxy (see note above) to work outside of it
